# 15 进程与 `fork`/`exec`

## 学习目标

完成本章后，你应该能够：

- 解释 PID、父子关系和进程地址空间隔离
- 区分进程树、进程组、会话和控制终端
- 正确处理 `fork` 的三种返回结果
- 使用 `exec` 替换子进程映像
- 用 `waitpid` 回收子进程并解释退出或信号状态
- 解释传统守护进程如何脱离终端，以及现代服务管理器的不同做法
- 避免 `fork` 与 stdio 缓冲、多线程和资源继承产生的常见问题

## 进程模型

程序是磁盘上的可执行文件，进程则是该程序的一次运行实例。同一个程序可以同时启动多次，每次运行都是不同的进程，并拥有各自的 PID 和运行状态。

可以把一个进程理解为“程序代码 + 当前执行状态 + 操作系统为它维护的资源”。这些资源主要包括：

- 虚拟地址空间：存放代码、全局变量、堆、栈和内存映射。
- 文件描述符表：记录进程当前打开的文件、管道、终端和 socket。
- 信号状态：记录信号处理方式、被阻塞的信号等信息。
- 执行线程：负责实际执行指令；一个进程至少有一个线程。
- 进程标识与父子关系：包括 PID、父进程 PID（PPID）、用户和进程组等信息。

PID 由内核分配，在进程存活期间用于标识该进程。PID 并不是永久唯一的：进程退出且被回收后，其 PID 以后可能分配给另一个进程。因此，不能把一个很早以前记录的 PID 永久当作某个特定进程的身份。

```c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    printf("PID=%ld PPID=%ld\n", (long)getpid(), (long)getppid());
    return 0;
}
```

例如，shell 启动这个程序时，程序进程的 PPID 通常就是 shell 的 PID。不过父进程可能先退出，此时子进程会被系统中的其他进程接管，所以稍后读取到的 PPID 可能发生变化。

## 进程之间有哪些关系

父子关系只是进程关系的一部分。在支持作业控制的 POSIX 系统中，进程还会组成进程组和会话，并可能关联一个控制终端。

| 层次 | 标识 | 主要作用 |
| --- | --- | --- |
| 单个进程 | PID | 标识一个正在运行的进程 |
| 父子关系 | PID、PPID | 表示谁创建了谁，父进程可以等待并回收子进程 |
| 进程组 | PGID | 把一组相关进程作为信号和作业控制的单位 |
| 会话 | SID | 组织一个或多个进程组，并描述它们与控制终端的关系 |

### 进程树：谁创建了谁

除系统启动阶段的特殊进程外，新进程通常由已有进程创建，因此系统中的进程会形成一棵进程树。例如，在交互式 shell 中执行一条包含管道的命令时，关系可能是：

```text
终端程序
└── shell
    ├── grep 进程 ──┐
    └── sort 进程 ──┴── 属于同一个管道作业
```

shell 是 `grep` 和 `sort` 的父进程。它负责创建管道、启动两个子进程，并在适当的时候通过 `waitpid` 回收它们。`grep` 和 `sort` 不一定互为父子；它们通常是兄弟进程，只是通过管道交换数据。

如果父进程在子进程之前退出，仍在运行的子进程不会因此自动退出。内核会把它重新指定给系统中的收养进程，例如 init 进程或配置为 subreaper 的进程。新的父进程之后负责回收它。

父子关系适合表达生命周期管理，但不能直接共享普通变量。父子进程需要通过管道、socket、共享内存、文件或信号等进程间通信机制交换信息。

### 进程组：把一项作业作为整体管理

进程组是一组相关进程的集合，每个进程组都有一个 PGID。shell 执行 `producer | consumer` 时，通常会把管道两端的进程放入同一个进程组。这样，终端产生的信号可以发送给整个前台作业，而不只是其中某个进程。

例如，用户按下 `Ctrl+C` 时，终端驱动通常向前台进程组发送 `SIGINT`。如果管道中的两个进程属于同一个前台进程组，它们都会收到信号：

```text
Ctrl+C
  │
  └── SIGINT ──▶ 前台进程组
                    ├── producer
                    └── consumer
```

这比 shell 逐个记录并通知所有进程更可靠。可以使用 `getpgrp` 查询当前进程组，使用 `setpgid` 调整进程所属的进程组。

### 会话与控制终端

会话包含一个或多个进程组。会话首进程的 PID 同时也是 SID。交互式登录或终端窗口通常对应一个会话，其中包括 shell、自身启动的前台作业和后台作业。

一个会话最多关联一个控制终端。控制终端负责前台进程组、终端输入以及 `Ctrl+C`、`Ctrl+Z` 等终端信号。普通后台作业虽然不占用 shell，但通常仍属于同一个会话，也没有真正脱离该终端。关闭终端时，它可能收到 `SIGHUP` 或因输入输出终端消失而受到影响。

因此，“命令末尾加 `&`”只表示让 shell 不阻塞等待该作业，不等于把程序变成了守护进程。

## 守护进程示例：让服务脱离终端

守护进程（daemon）是长期在后台运行、通常不直接与交互式终端通信的服务进程，例如定时任务服务、日志服务或网络服务器。传统 Unix 程序会主动脱离启动它的 shell 和控制终端，使服务不依赖某个终端窗口持续存在。

### 传统双重 `fork` 的关系变化

传统守护化过程经常使用两次 `fork`：

```text
shell
└── 原进程
    └── 第一次 fork 的子进程
        ├── setsid：创建新会话，脱离原控制终端
        └── 第二次 fork 的子进程：最终守护进程
```

具体过程如下：

1. 第一次 `fork` 后让原进程退出。新子进程继承原进程的 PGID，但获得不同的 PID，因此它不是进程组组长，能够调用 `setsid`。
2. 子进程调用 `setsid`，成为新会话的会话首进程和新进程组的组长，并脱离原控制终端。
3. 再执行一次 `fork`，让会话首进程退出。最终子进程不再是会话首进程，从而避免它以后意外获得新的控制终端。
4. 设置文件创建掩码和工作目录，避免继承调用者不合适的 `umask`，也避免长期占用某个可卸载目录。
5. 关闭或重定向标准输入、标准输出和标准错误，因为原终端已经不应再作为服务的输入输出设备。

下面的函数展示这一传统过程：

```c
#include <fcntl.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <unistd.h>

static int redirect_standard_fds(void) {
    int null_fd = open("/dev/null", O_RDWR);
    if (null_fd == -1) {
        return -1;
    }

    if (dup2(null_fd, STDIN_FILENO) == -1 ||
        dup2(null_fd, STDOUT_FILENO) == -1 ||
        dup2(null_fd, STDERR_FILENO) == -1) {
        close(null_fd);
        return -1;
    }

    if (null_fd > STDERR_FILENO) {
        close(null_fd);
    }
    return 0;
}

static int daemonize(void) {
    pid_t pid = fork();
    if (pid == -1) {
        return -1;
    }
    if (pid > 0) {
        _exit(0);              /* 原进程退出。 */
    }

    if (setsid() == -1) {
        return -1;
    }

    pid = fork();
    if (pid == -1) {
        return -1;
    }
    if (pid > 0) {
        _exit(0);              /* 会话首进程退出。 */
    }

    umask(0);
    if (chdir("/") == -1) {
        return -1;
    }
    return redirect_standard_fds();
}
```

调用 `daemonize` 成功后，当前代码运行在最终的守护进程中。此时不能再依赖终端上的 `printf` 查看状态，因为标准输出和标准错误已经指向 `/dev/null`。实际服务应把日志写入日志系统、专用日志文件或服务管理器提供的日志通道。

这段代码只演示进程关系和终端脱离过程，还不是完整的生产级服务。实际守护进程还需要处理：

- 用信号实现正常停止和重新加载配置。
- 回收自己创建的子进程，避免产生僵尸进程。
- 明确关闭不再需要的继承 fd，并为其他 fd 设置 `FD_CLOEXEC`。
- 适当降低用户和组权限，限制可访问资源。
- 向启动方报告初始化成功或失败；不能让最初的父进程无条件退出后就假定服务已经可用。
- 避免重复启动。传统程序有时使用 PID 文件，但必须处理 PID 复用、文件锁和异常退出等问题。

### 现代服务管理器下通常不要自行守护化

在 Linux 的 `systemd`、macOS 的 `launchd` 或容器运行环境中，服务通常应保持前台运行，不要自行执行双重 `fork`。服务管理器已经负责：

- 在后台启动和监控进程。
- 收集标准输出和标准错误日志。
- 传递停止、重载等信号。
- 在进程异常退出后按策略重启。
- 管理运行用户、环境变量和资源限制。

这时进程关系更直接：

```text
systemd / launchd / 容器运行时
└── 服务主进程（保持前台运行）
    └── 可选的工作进程
```

服务管理器通常需要跟踪服务主进程的 PID 和退出状态。程序自行双重 `fork` 反而可能让管理器跟踪到已经退出的中间进程。因此，是否守护化取决于运行环境：独立运行的传统 Unix 服务可以使用守护化流程；由现代服务管理器托管的程序通常提供 `--foreground` 或类似模式并保持前台运行。

### 守护进程怎样使用子进程

守护进程不一定只有一个进程。网络服务器常使用一个主进程管理多个工作进程：

```text
服务管理器
└── 主进程
    ├── 工作进程 1
    ├── 工作进程 2
    └── 工作进程 3
```

主进程可以负责读取配置、监听管理信号和创建工作进程；工作进程负责处理具体请求。某个工作进程异常退出时，主进程通过 `waitpid` 得知退出原因，再决定记录错误、补充新工作进程或关闭整个服务。

这种结构利用了进程地址空间隔离：一个工作进程崩溃通常不会直接破坏其他工作进程的内存。但进程间共享状态需要额外设计，例如使用共享内存、数据库、socket 或由主进程集中管理。

## `fork` 创建子进程

`fork` 根据当前进程创建一个新进程。调用 `fork` 的进程称为父进程，新创建的进程称为子进程。

理解 `fork` 的关键是：执行 `fork` 之前只有一个进程；调用成功之后有父、子两个进程，而且两个进程都会从 `fork` 返回后的下一条语句继续执行。它不是让同一个进程返回两次，而是让两个进程各返回一次。内核通过不同的返回值，让程序判断当前位于父进程还是子进程：

| 返回值 | 所在进程 | 含义 |
| --- | --- | --- |
| `-1` | 原进程 | 创建失败，没有子进程 |
| `0` | 子进程 | 当前正在执行子进程路径 |
| 正数 | 父进程 | 返回值是新子进程 PID |

```c
pid_t pid = fork();
if (pid == -1) {
    perror("fork");
    return 1;
}
if (pid == 0) {
    /* 子进程路径 */
    _exit(0);
}
/* 父进程路径，pid 是子进程 ID。 */
```

调用成功后的执行过程可以画成：

```text
原进程执行到 fork()
          │
          ├── 父进程：fork() 返回子进程 PID，继续执行后续代码
          └── 子进程：fork() 返回 0，也继续执行后续代码
```

父进程和子进程谁先运行没有保证，完全由调度器决定。因此，不能依赖两边 `printf` 的先后顺序。需要确定顺序时，应使用 `waitpid`、管道、信号量等同步机制。

### 父子进程的内存为什么互不影响

父子进程拥有独立的虚拟地址空间。`fork` 刚返回时，两边的变量内容看起来完全相同，但之后任一进程修改变量，都不会改变另一个进程中的副本：

```c
int value = 10;
pid_t pid = fork();

if (pid == -1) {
    perror("fork");
    return 1;
}
if (pid == 0) {
    value = 20;
    dprintf(STDOUT_FILENO, "child: value=%d address=%p\n",
            value, (void *)&value);
    _exit(0);
}

printf("parent: value=%d address=%p\n", value, (void *)&value);
```

父子进程打印出的指针值可能相同，因为这个地址是各自地址空间中的虚拟地址；相同的虚拟地址不代表它们正在操作同一个 C 对象。子进程把 `value` 改为 `20` 后，父进程中的 `value` 仍然是 `10`。

操作系统通常使用写时复制（copy-on-write，COW）实现这一点。`fork` 后，父子进程可以暂时共享相同的物理内存页；当其中一方尝试写入时，内核才复制相关页面，并让写入方修改自己的副本。这样既维持了地址空间隔离，又避免在 `fork` 时立即复制全部内存。

### 文件描述符继承与共享文件偏移

子进程会继承父进程已经打开的文件描述符。父子进程中的描述符数字虽然位于两张独立的描述符表中，但通常指向内核中的同一个 open file description。该内核对象保存当前文件偏移和部分状态标志。

因此，如果父进程在 `fork` 前打开一个文件，子进程读取 10 字节使文件偏移前进，父进程随后从同一个继承的描述符读取时，通常会从新的偏移继续，而不是重新从文件开头读取。

```text
父进程 fd 3 ──┐
              ├── 同一个 open file description ── 文件
子进程 fd 3 ──┘          当前偏移：共享
```

这里的“共享”指两边描述符引用同一个内核打开文件状态，不表示两个进程共享整个地址空间。如果父子进程不应共同使用某个描述符，应在不需要它的一方尽早调用 `close`。

## stdio 缓冲与 `fork`

`printf` 等 stdio 函数通常不会每次都立即调用内核写出数据，而是先把内容放入用户态缓冲区。终端上的 `stdout` 通常按行缓冲，输出到文件或管道时通常是全缓冲，但具体行为还取决于实现和流配置。

`fork` 会复制进程的用户态内存，因此也会复制尚未写出的 stdio 缓冲区。如果缓冲区中已有一份文本，父子进程之后都通过 `exit` 或其他方式刷新流，这份文本就可能被写出两次。

例如，下面的文本没有换行。把输出重定向到文件时，它很可能在 `fork` 前仍留在缓冲区中：

```c
printf("starting");
pid_t pid = fork();
```

调用成功后，父子进程各自拥有一份包含 `starting` 的缓冲区；如果两边都正常调用 `exit`，文件中可能出现 `startingstarting`。这不是 `fork` 重复执行了 `printf`，而是它复制了 `printf` 已经产生但尚未写出的数据。

在 `fork` 前刷新所有已打开的输出流，可以避免复制待输出内容：

```c
printf("starting\n");
if (fflush(NULL) == EOF) {
    perror("fflush");
    return 1;
}
pid_t pid = fork();
```

还要区分 `exit` 和 `_exit`：

- `exit` 会刷新 stdio 流，并运行通过 `atexit` 注册的处理器。
- `_exit` 直接结束进程，不刷新 stdio，也不运行用户态退出处理器。

所以，子进程调用 `_exit` 可以避免再次刷新从父进程复制来的缓冲区；但子进程在 `_exit` 前通过 `printf` 新写入缓冲区的内容也可能丢失。`fork` 后准备立即 `exec` 的子进程通常使用 `write` 或 `dprintf` 报告 `exec` 错误，然后调用 `_exit`。

## `waitpid` 与子进程状态

子进程退出时，其地址空间和大部分资源会被释放，但内核仍需保留 PID、退出原因和资源使用情况等少量信息，让父进程能够得知子进程如何结束。已经退出、但尚未被父进程读取状态的子进程称为僵尸进程。

僵尸进程不会继续执行代码，也不会继续占用原来的地址空间，但会占用进程表项。父进程应调用 `wait` 或 `waitpid` 回收子进程。这里的“回收”不是终止仍在运行的子进程，而是读取并清除一个已经结束的子进程所留下的状态。

```c
#include <errno.h>
#include <sys/wait.h>

int status;
pid_t waited;
do {
    waited = waitpid(pid, &status, 0);
} while (waited == -1 && errno == EINTR);

if (waited == -1) {
    perror("waitpid");
} else if (WIFEXITED(status)) {
    printf("exit=%d\n", WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
    printf("signal=%d\n", WTERMSIG(status));
}
```

`waitpid(pid, &status, 0)` 中各参数的含义是：

- `pid`：等待这个特定的子进程。
- `&status`：让内核写入编码后的终止状态。
- `0`：如果子进程还没有结束，就阻塞等待。

调用可能被信号中断并以 `EINTR` 失败，因此示例使用循环重试。只有 `waitpid` 成功返回后，`status` 中才包含可解释的状态。

`status` 不是子进程的普通退出码，而是同时编码了“如何结束”和相关值。必须先用宏判断结束类型，再读取对应信息：

- `WIFEXITED(status)` 为真：子进程调用了 `exit`、`_exit`，或从 `main` 返回；此时用 `WEXITSTATUS(status)` 读取退出码。
- `WIFSIGNALED(status)` 为真：子进程被未捕获的信号终止；此时用 `WTERMSIG(status)` 读取信号编号。

如果不先判断就调用 `WEXITSTATUS`，可能把“被信号终止”等其他状态中的位错误地解释成退出码。

## `exec` 替换进程映像

`exec` 族函数不会创建新进程，而是让当前进程开始运行另一个程序。成功后，原程序的代码、全局数据、堆和栈会被新程序的进程映像替换，但它仍是同一个进程，所以 PID 不变。

这也解释了为什么 shell 通常组合使用 `fork` 和 `exec`：shell 不能直接 `exec` 外部命令，否则 shell 自身会被替换，无法继续接收下一条命令。它先 `fork` 创建子进程，再让子进程 `exec` 目标程序；父进程仍然保留 shell 自身。

```text
子进程调用 exec 前                    exec 成功后
┌────────────────────┐               ┌────────────────────┐
│ 原程序的代码/数据   │  ─────────▶   │ 新程序的代码/数据   │
│ PID = 1234          │               │ PID = 1234          │
└────────────────────┘               └────────────────────┘
```

`exec` 成功后不会返回，因为调用它的旧程序已经不存在；CPU 会从新程序的入口开始执行。只有加载或启动新程序失败时，`exec` 才返回 `-1` 并设置 `errno`：

```c
char *const arguments[] = {"ls", "-l", NULL};
execvp(arguments[0], arguments);

/* 只有失败才执行。 */
int error = errno;
dprintf(STDERR_FILENO, "execvp failed: %s\n", strerror(error));
_exit(127);
```

常见名称可以拆解：

- `l`：参数以列表传入
- `v`：参数以 `argv` 数组传入
- `p`：按 `PATH` 搜索程序
- `e`：调用者显式提供环境数组

示例中的 `arguments[0]` 是要查找并执行的程序名，整个 `arguments` 则是传给新程序的 `argv`。数组必须以 `NULL` 结束。按照惯例，`argv[0]` 表示程序名，所以这里也填写 `"ls"`。

## `fork` + `exec` + `waitpid`

```text
父进程 fork
   ├── 子进程：关闭无关 fd -> exec
   └── 父进程：关闭无关 fd -> waitpid
```

父进程必须处理 `fork` 失败；子进程必须处理 `exec` 失败；父进程必须判断子进程是正常退出还是被信号终止。

下面是一段可以串起完整流程的简化代码：

```c
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    if (fflush(NULL) == EOF) {
        perror("fflush");
        return 1;
    }

    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return 1;
    }

    if (pid == 0) {
        char *const argv[] = {"ls", "-l", NULL};
        execvp(argv[0], argv);

        /* 运行到这里说明 execvp 失败。 */
        int error = errno;
        dprintf(STDERR_FILENO, "execvp: %s\n", strerror(error));
        _exit(127);
    }

    int status;
    pid_t waited;
    do {
        waited = waitpid(pid, &status, 0);
    } while (waited == -1 && errno == EINTR);

    if (waited == -1) {
        perror("waitpid");
        return 1;
    }
    if (WIFEXITED(status)) {
        printf("child exit status: %d\n", WEXITSTATUS(status));
    } else if (WIFSIGNALED(status)) {
        printf("child terminated by signal: %d\n", WTERMSIG(status));
    }
    return 0;
}
```

这段代码中有三个互相独立的错误分支：`fork` 失败发生在父进程中；`execvp` 失败发生在子进程中；`waitpid` 失败发生在等待子进程的父进程中。不能用一次错误检查替代另外两次。

现代 POSIX 还提供 `posix_spawn`，可在许多“创建后立即 exec”的场景中减少 fork 后准备工作的复杂度，尤其适合多线程程序。

## 多线程程序中的 `fork`

多线程进程调用 `fork` 后，父进程中的所有线程继续存在，但子进程只复制调用 `fork` 的那个线程。这会产生一个不直观的问题：子进程复制了整个地址空间，其中也包括 mutex 等同步对象的状态；但是，原来持有某个 mutex 的其他线程并没有被复制到子进程中。

例如，线程 A 持有某个库内部的锁，线程 B 此时调用 `fork`。子进程中只有线程 B，锁却仍可能显示为“已被线程 A 持有”。如果子进程在 `exec` 前调用一个需要该锁的库函数，它可能永久等待，因为能够解锁的线程 A 在子进程中根本不存在。

POSIX 因此规定，多线程程序 `fork` 后、`exec` 前的子进程原则上只能调用 async-signal-safe 函数。很多看似普通的函数，包括依赖内部锁或动态内存分配的函数，都不满足这一要求。

实际工程通常选择：

- 在创建线程前启动子进程
- fork 后立即 exec
- 使用 `posix_spawn`
- 必要时谨慎使用 `pthread_atfork`

## 环境与文件描述符继承

子进程继承父进程环境变量的副本。进程调用 `setenv` 修改自己的环境后，变化只影响当前进程，以及它以后通过 `fork`/`exec` 启动的程序；它不能反向修改父进程或启动它的 shell。这就是为什么在一个普通子进程中执行 `cd` 或修改环境变量，不能改变父 shell 的工作目录或环境。

`fork` 会继承打开的 fd；默认情况下，这些 fd 在 `exec` 后也继续存在。敏感或新程序不需要使用的 fd 应设置 close-on-exec：

```c
int fd = open(path, O_RDONLY | O_CLOEXEC);
```

也可以通过 `fcntl` 设置 `FD_CLOEXEC`。设置后，`fork` 得到的子进程仍能看到该 fd，但成功执行 `exec` 时内核会自动将它关闭。

管道尤其容易因 fd 继承出错。读取端只有在所有写入端都关闭后才会读到 EOF。如果父进程或某个无关子进程意外保留了一个写入端，即使真正的写入进程已经退出，读取方仍会认为“还有人可能继续写”，因而一直等待。

## 进程退出

- `return` 离开 `main` 等价于调用 `exit`。
- `exit` 刷新并关闭 C 流，调用 `atexit` 处理器。
- `_exit` 立即把状态交给内核，不运行用户态清理。

fork 后 exec 失败的子进程通常使用 `_exit(127)`，避免重复刷新从父进程复制来的缓冲区。`127` 是 shell 中常用于表示“命令无法执行或未找到”的约定值，不是 `exec` 接口强制规定的值；程序也可以根据自己的协议选择其他退出码。

## 常见错误

- 忽略 `fork` 失败并把父进程路径当作成功
- 未检查 `waitpid` 就读取 `status`
- 未判断 `WIFEXITED` 就调用 `WEXITSTATUS`
- fork 前没有刷新 stdio，导致重复输出
- `_exit` 前使用缓冲输出，导致内容丢失
- 父子进程没有关闭不需要的管道端点
- exec 前泄漏本应 close-on-exec 的 fd
- 多线程子进程在 exec 前调用可能加锁的库函数
- 把后台作业误认为已经脱离终端的守护进程
- 在 `systemd`、`launchd` 或容器中无必要地执行双重 `fork`
- 守护进程创建子进程后不调用 `waitpid`，留下僵尸进程

## 检查点

1. `fork` 后为什么父子进程可能打印相同的指针值？
2. `exec` 成功后 PID 是否改变？
3. 为什么只有 `WIFEXITED` 为真才能读取退出码？
4. 为什么 fork 前未刷新的输出可能出现两次或完全消失？
5. 进程组和父子关系分别解决什么问题？
6. 为什么传统守护化要调用 `setsid`，第二次 `fork` 又解决什么问题？
7. 为什么由服务管理器托管的程序通常应该保持前台运行？
