# 04 正确测量和优化

## 学习目标

建立包含正确性、热身、重复测量、边界成本和现实输入的基准方法，并正确解释加速比。

## 运行基准

```bash
make benchmark
```

`benchmark.py` 比较三个等价实现：Python 循环、`ctypes` 动态库和 Python/C API 扩展。它先断言结果相同，再运行 7 次并报告中位数。

输出格式如下，数字因机器负载和 Python 版本而异：

```text
implementation        seconds    speedup
Python loop           ...          1.0x
ctypes                ...          ...x
Python/C API          ...          ...x
```

不要把一次运行或某台机器的加速比写成普遍结论。

## 为什么使用中位数

计时会受到调度、温度、后台程序和缓存状态影响。重复运行后，中位数不容易被偶发慢样本扭曲。更严谨的项目可使用 `pyperf`，控制热身、子进程和系统稳定性。

本例在计时之外完成导入和结果检查，避免把一次性加载成本混进热点。实际应用如果进程很短，导入时间本身也应单独测量。

## 公平比较

公平不意味着实现逐行相同，而是：

- 输入、输出和定义域一致。
- 算法复杂度一致。
- 错误和溢出语义已定义。
- 计时范围符合要优化的真实路径。
- 没有把准备数据放在一边，却把另一边的数据准备算入时间。

例如公式 `n(n+1)(2n+1)/6` 是更好的平方和算法，但拿它和逐项 C 循环比较是在比较算法，而不是语言执行成本。生产代码当然应优先选择公式。

## 边界粒度

假设跨边界一次耗时为 `B`，C 计算为 `C`，调用 `N` 次的开销近似：

```text
细粒度：N * (B + C)
批量：  B + N * C
```

这就是为什么 `add_int32` 适合教学 ABI，却不是值得逐次替换 Python 加法的优化。把整个循环、数组或消息批次交给 C 更可能获益。

设计批量接口时也要测量数据复制：`sum_doubles` 将 Python iterable 转成新列表和 C 数组。若计算只是一次求和，Python 内置 `sum` 或连续缓冲区接口可能更合适。

## Amdahl 定律

如果热点只占总耗时的 40%，即使把它加速到无限快，整体加速也不会超过：

```text
1 / (1 - 0.4) = 1.67x
```

因此应优化占比高的路径，并重新做端到端测量。微基准快 50 倍不代表应用也会快 50 倍。

## 优化检查表

1. 用 profiler 找到真实热点。
2. 建立 Python 参考实现和边界测试。
3. 定义整数范围、错误语义和数据所有权。
4. 先改算法，再考虑语言迁移。
5. 尽量批量跨越 Python/C 边界。
6. 比较结果，再测量多次。
7. 测端到端收益、内存和并发影响。
8. 在 CI 支持的 Python 与操作系统组合上构建测试。

## 动手练习

1. 把 `LIMIT` 改为 `10`、`1_000` 和 `1_000_000`，记录哪种规模下边界成本最明显。
2. 写一个基准，在 Python 循环中调用一百万次 `add_int32`，再与一次批量 C 调用比较。
3. 用平方和公式实现第四个版本。把“算法改进”和“C 加速”分别报告，不混成一个结论。
