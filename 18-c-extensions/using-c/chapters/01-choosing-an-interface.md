# 01 选择 C 接口

## 学习目标

判断一个 Python 问题是否适合用 C 优化，并在 `ctypes`、Python/C API 和 Cython 之间作出有依据的选择。

## 从热点开始，而不是从 C 开始

程序总耗时可以粗略拆成：

```text
总耗时 = Python 计算 + I/O 等待 + 边界转换 + C 计算
```

C 只能直接减少其中一部分。网络请求慢、数据库查询慢或算法复杂度不合理时，重写循环通常没有价值。先用标准库定位热点：

```bash
python3 -m cProfile -s cumulative program.py
python3 -m timeit -s 'data = list(range(10000))' 'sum(data)'
```

`cProfile` 适合找函数级热点，`timeit` 适合比较小段代码。分析时使用接近真实规模的输入，并分别观察 CPU 时间、内存和端到端延迟。

## C 为什么可能更快

Python 循环中的每次运算通常要处理 Python 对象、动态类型和解释器执行。类型明确的 C 循环可以在连续机器值上工作：

```text
Python 循环每轮：取字节码 -> 查对象类型 -> 执行操作 -> 创建/更新对象
C 循环每轮：     读取整数 -> 乘法 -> 加法 -> 下一轮
```

但进入 C 前仍有参数解析和函数调用成本。下面通常适合迁移：

- 大量数值、字节或文本扫描。
- 压缩、解析、图像处理和密码学等已有成熟 C 库的工作。
- 能一次传入一批数据并在 C 内完成的算法。
- 性能分析确认占据显著 CPU 时间的稳定热点。

下面通常不适合：

- 每次调用只做极少工作。
- 需要频繁访问任意 Python 对象或回调 Python。
- 业务逻辑变化很快，性能不是实际瓶颈。
- 用更合适的算法或批量数据库操作即可解决。

## 选择路径

依次回答：

1. 已经存在一个稳定 C ABI 吗？有则先试 `ctypes`。
2. 需要创建原生 Python 类型、使用 buffer protocol 或精细控制异常吗？考虑 Python/C API。
3. 热点主要是现有 Python 循环，而且团队接受构建依赖吗？考虑 Cython。
4. NumPy、SciPy 或其他成熟库已经完成相同操作吗？优先复用。

```text
已有 C 库？ --是--> ctypes
    |
    否
    v
需要深度操作 Python 对象？ --是--> Python/C API
    |
    否
    v
渐进加速 Python 算法？ --是--> Cython
```

真实项目可以组合使用，例如用 Cython 包装一个 C 库，或用 Python/C API 暴露底层缓冲区。

## 加速目标必须包含正确性

Python `int` 是任意精度整数，C 的 `int64_t` 范围有限。Python 下标越界抛出异常，错误的 C 指针访问可能直接崩溃。性能目标应写成：

> 对已定义的输入范围产生与 Python 基线相同的结果，并在代表性负载上降低测得的运行时间。

本教程的 C 接口会主动检测负数和整数溢出。任何加速都先通过 `test_using_c.py`，再运行 `benchmark.py`。

## 理解检查

1. 一个 API 每秒调用一百万次，每次只做两个整数相加，迁移到 C 一定更快吗？为什么？
2. 一个请求 90% 的时间在等待数据库，计算热点加速 10 倍后，端到端收益为什么有限？
3. 已有供应商提供的 `.dylib` 和 C 头文件时，哪条路径的初始成本最低？

预期结论：边界调用可能吞掉微小计算收益；只能优化总时间中的计算部分；已有 C ABI 时先用 `ctypes` 验证集成最直接。

## 动手练习

选择一个自己的 Python 程序，用 `cProfile` 找出累计耗时最高的三个函数。对每个函数记录它是 CPU 密集、I/O 密集还是边界调用，并写出“不改、换算法、复用库、迁移到 C”四种决策之一。
