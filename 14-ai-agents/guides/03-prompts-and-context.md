# 03 Prompt、消息与上下文工程

## 学习目标

能够构造模型真正需要的上下文，区分指令、会话、工具观察、记忆和检索资料，并用结构化输出替代脆弱文本解析。

## 概念模型

上下文通常按以下层次组装：平台与安全策略、应用指令、当前任务、必要历史、召回的 memory、RAG 证据、工具结果。越靠后的不可信内容不能覆盖更高层策略。

token window 是容量上限，不是应填满的目标。保留与任务相关的信息，并为模型输出和工具结果预留预算。

## 执行路径

`Message` 显式记录 role。上下文构建器应先选择信息，再序列化消息；不要把所有数据拼成一个字符串。需要机器消费的计划、分类或参数应使用 JSON schema/Pydantic 等结构验证。

## 底层机制

模型看到的是序列化 token，没有真正的“数据库记忆”。每次调用都要重新提供需要的信息。temperature 影响采样，不解决事实性、权限或 schema 校验问题。

## 检查点与练习

列出一次工具调用前后消息的 role 顺序。为一个 `ResearchPlan` 设计包含 `questions: list[str]` 与 `needs_approval: bool` 的 schema，并考虑缺字段和额外字段应如何处理。

## 常见错误与生产注意

- 无限制追加历史导致成本增长与注意力稀释。
- 把 RAG 文档放入 system 指令层。
- 用正则从自由文本提取关键业务字段。
- 在日志或调试 prompt 中泄露密钥与个人数据。
