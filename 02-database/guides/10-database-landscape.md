# 10 数据库类型地图

## 学习目标

根据访问模式、事务要求和扩展方式选择数据存储，而不是根据流行度选择。

| 类型 | 典型产品 | 擅长 | 不适合替代 |
| --- | --- | --- | --- |
| 关系型 | PostgreSQL、MySQL、SQLite | 事务、约束、JOIN、结构化查询 | 所有缓存或全文检索场景 |
| 键值/缓存 | Redis | 低延迟缓存、计数器、短期状态 | 核心事实的唯一持久化来源 |
| 文档型 | MongoDB | 聚合文档、灵活嵌套结构 | 强关系和大量跨文档事务 |
| 搜索引擎 | Elasticsearch/OpenSearch | 全文检索、相关性、日志分析 | 核心交易数据库 |
| 列族 | Cassandra | 高写入吞吐、按已知键访问、跨节点扩展 | 临时复杂 JOIN 查询 |
| 时序 | TimescaleDB、InfluxDB | 时间窗口、指标、降采样 | 通用业务关系建模 |
| 图数据库 | Neo4j | 多跳关系遍历 | 普通 CRUD 业务表 |
| 向量数据库 | Milvus、Qdrant | 近似最近邻、语义相似度 | 权威元数据和复杂事务 |

## Polyglot Persistence

真实系统可能组合多种存储：PostgreSQL 保存权威业务数据，Redis 做缓存，OpenSearch 做全文搜索，Milvus 保存向量索引。组合会增加同步、恢复、监控和一致性成本，因此先从能满足需求的最少存储开始。

向量数据库专题位于 `vector-databases/milvus/`。向量数据库中的记录 ID 应能关联回关系数据库中的权威实体；删除或更新必须考虑两个系统之间的最终一致性。

## 选择问题

1. 最重要的读取和写入模式是什么？
2. 是否需要跨多行或多实体事务？
3. 数据规模、吞吐和延迟目标是什么？
4. 哪个系统是事实来源？
5. 如何备份、恢复、迁移和删除数据？
6. 团队能否承担新的运维和一致性成本？
